Strict structured decisions — October 30, 2026

Scheduled generation now returns a typed decision envelope. The host validates
the entire response and dispatches explicit operations through the existing
gateway. Main, Economy, Military, Communication, strategic reviews and both
peace-consultation phases use strict output schemas on every turn, including
continuations and resumed threads. Generated JavaScript is no longer the
scheduled model interface. Authentication, model selection, ownership and the
concurrent scheduler remain in place.

The implementation has local contract, recovery and provider-boundary coverage.
It is not accepted as a demonstrated gameplay improvement. The live screen
violated its request cap: 16 host turn/start calls produced at least 20 provider
requests, because four rejected exec calls triggered automatic continuations
inside Codex. This was an accounting error in the screening harness. No execution
tool ran, no screened decision was dispatched, and further live calls were
stopped. The screen is closed; its checked-in utility now supports only offline
schema preparation and audit. One stalled request has no reported usage.

Interface and enforcement

decision_contracts.py defines inspect, act, finish, wait and submit_report
variants. Role schemas contain their complete permitted operation set; there is
no operation-selection round trip. Inspections and actions have separate batches
of 1–12 entries. Completion and waiting are standalone decisions. Report phases
use their existing typed report models. Strategic review inspections retain their
frozen source and grounding checks. Decisions backends retain their existing
closed-choice contracts and fallback checks; these are separate from strict
generative JSON output and are not included in the generative schema claim.

Command variants come from the canonical command definitions, with common
intent and military reviewAfter metadata outside the repeated variants. Native
inspection arguments, typed memory amendments, coordination and diplomacy are
also closed contracts. Dynamic game options remain observation data, rather than
state-dependent schema enums. Startup instructions no longer duplicate full
schema listings; descriptions retain consequences, prerequisites, ownership and
guidance for ambiguous choices. Social promises remain exact, authored,
nonbinding text. They never prohibit a native-legal action.

strict_schema.py produces both the provider representation and its runtime
validator from these contracts. It closes every object, makes wire properties
required, removes wire defaults, uses supported nested unions and shares
structurally identical definitions with collision checks. Compact schemas omit
redundant titles while preserving descriptions and constraints. Null in a wire
optional means omission. If the canonical optional itself accepts null, a
{value: null} wrapper explicitly clears it; {value: X} sets it. Omitted patch
fields remain unchanged, and canonical defaults still apply where appropriate.
Unsupported keywords, arbitrary objects, unsupported intersections, ambiguous
oneOf conversions and unsupported formats fail compilation. Canonical semantic
validators additionally enforce constraints such as duplicate-free lists that
the supported provider schema subset cannot express.

Every scheduled turn/start supplies outputSchema. CodexProcess rejects a missing
schema before sending the request. Thread start and resume supply no dynamic
tools; inherited MCP servers are explicitly disabled, along with shell, unified
execution, code mode and other execution features. Local captures from the
installed Codex 0.164 show strict=true and the expected schema on all seven call
families, their continuations and resumed turns. They show no executable tool or
MCP call. Codex still advertises its built-in request_user_input tool outside Plan
mode; interactive RPCs are rejected. Consequently the accurate claim is no
model-accessible execution or MCP, not an entirely empty provider tools array.
Hallucinating a disabled tool can still cause internal model continuations.

Only completed final responses are parsed. An explicit final answer takes
priority over later unphased messages. Refusals, unfinished generations, invalid
JSON and failed schema or canonical argument validation dispatch nothing.
Repairs are bounded and journaled. Receipt continuations use toolOutput on the
same thread. Fresh role activations still create fresh threads as before.

Execution, delivery and recovery

structured_decisions.py persists a host decision identity before generation and
all child operation identities before dispatch. It validates the complete batch
before executing any child. Actions run in order, stopping on rejection,
uncertainty, ownership/coordination changes, changed targets, unavailable state,
negotiation suspension or an operation requiring reconsideration. Each receipt
identifies its operation; all remaining entries are explicitly unexecuted.

The loop records the context actually delivered to the model separately from
intermediate gateway observations. Receipt snapshots retain observation revision,
entity fingerprints, inspected detail credits, proposal fingerprints and memory
and war versions. Unrelated receipts and hidden refreshes cannot grant a preview
or revision credit. A sibling action may leave an independently inspected target
usable, but cannot confer permission based on unseen information. Gateway
visibility, native legality, role ownership, previews and emergency overrides
still apply at dispatch.

Military completion binds the delivered review basis in the host. The model
supplies dispositions for delivered targets, including paginated reviews. It
cannot invent a basis field. Zero remaining targets need no fabricated review.
The existing completion checks still require explicit dispositions when targets
remain. Main waits preserve exact request IDs and deliver current outcomes and
fresh context through the receipt continuation.

Confirmed receipts replay without repeating native actions. If execution was
interrupted, deterministic operation/request identities are reconciled against
the native receipt before any retry. An uncertain outcome remains uncertain;
an unexecuted child after restart needs a new decision. Epoch checks prevent
replaying an old decision across rewind. Pure report validation can drain during
a checkpoint hold; its controller separately fences publication against rewind.

Diagnostics and accounting

The read-only civ-agent match failures command correlates generation, schema validation, gateway
dispatch and native receipts. Evidence contains schema fingerprints, decision and
operation identities, execution status, argument/state/ownership/legality/
transport categories, partial-batch status and retrievable native receipts.
Receipt replay and bundle wrappers are not counted as additional failed actions.
A partial batch is a separate incident, not another failed child call. Pending
calls without an outcome are not assumed to have failed. Invalid-generation
evidence stores an output hash and size, not raw reasoning. Credentials and raw
reasoning are excluded from the new diagnostics and audit report.

Usage groups by role, model phase, provider, model and schema fingerprint. Main
and Military peace consultations remain distinct phases. Schema characters and
UTF-8 bytes, instruction sizes, initial observation sizes, continuation sizes and
output sizes are separate from actual tokens. These sizes are storage measures
and only proxies for token cost; no tokenizer estimate is presented as usage.
Actual input, cached input, uncached input, output and repair usage come from
cumulative thread counters, differenced against the durable decision baseline.
Using only the last-response counter would omit internal continuations.
Restart restores that baseline from the decision journal if a crash preceded the
controller record save, avoiding double-counting earlier thread usage.
Unknown usage remains marked unknown. Provider inference, HTTP transport,
WebSocket transport and tool-call counts from accounting.sqlite3 remain separate
from host decisionRequests; they must not be added as interchangeable requests.

Live paired screen: measured evidence and exceptions

Four saved contexts were reused across Luna and Terra at medium effort with
verbose and compact schemas. Main, Economy and Military came from the retained
Arabia context in pangaea-v4-20261030 g0001; Communication used a retained Greece
context from two-continents-v3 g0003. screen-contexts.json and the prepared context
files record source histories and hashes. This was a one-response screen per
cell, not a played turn or a full game. No generated decisions were executed.

The original 16-cell result is preserved in live-screen-v3/results.json. The
corrected offline audit is live-screen-v3/usage-audit.json. It deduplicates
per-response token records by provider response ID and reads tool names only.
The first two setup attempts made no model requests. The working live runner is
retained as runner-original.py for provenance and is not the checked-in runner.

Existing gameplay evidence and acceptance limits

The preserved Decision-efficiency-screening-2026-10-30 report covers four earlier
ten-turn trials paired with four reused controls and reports 30.80% lower total
tokens for Luna and 9.13% for Terra, with mixed peace/conquest choices. Those
results support the preceding context-delivery work, not this new decision loop.
They were reused as background evidence; full games were not rerun. Dedicated
Communication and live strategic/peace reports are not validated for quality by
this screen. Runtime alone is not an acceptance measure.

Strict shape enforcement does not establish good strategy, full player-action
coverage, universal native legality or a complete privacy boundary. Semantic
mistakes still reach gateway rejection, and uncertain native outcomes still need
reconciliation. The live request cap was not met, the stalled cell remains
unresolved, and post-screen fixes have no live rerun. These are explicit limits
of this delivery, not successful acceptance criteria.
