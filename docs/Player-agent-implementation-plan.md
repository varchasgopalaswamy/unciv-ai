**Implementation plan: external agents as ordinary Unciv players**

Created 2026-09-06 against `d77a312ed6ba0d127fe4efdfbcdc9f4918c0b5fa`. Status: proposed; all implementation steps below are pending. The companion [source review](Player-agent-API-review.md) explains the present API inventory and concrete permission gaps. This file is the implementation backlog; completing the review or writing this plan does not complete any implementation step.

For the subsequently requested headless deployment, see [Headless player agents without completing the View refactor](Headless-player-agent-path.md). That alternative retains complete player action/information coverage while moving the player API and most privacy projections into a trusted downstream host. The desktop attachment and broad View/UI migration dependencies below are not prerequisites for that route.

**Outcome and scope**

Several independently connected agents can control different players in one running game, with the actions and information available to an ordinary human. One trusted host owns the game; each session is bound to a civilization. Human UI and agent commands share validation and information policies. Queries, previews, options, errors, notifications and update metadata obey the same player permissions.

Cover the bundled **Vanilla and Gods & Kings** rulesets, including their nation-specific abilities. Exclude custom mods, simultaneous-turn redesign, migration of the entire internal AI, arbitrary script/unique execution, and new gameplay mechanics. An existing generic engine handler is not evidence that an ability is in scope: use bundled definitions plus reachable human controls. For example, Great Admiral change-port is included; the commented-out fleet-heal ability is not.

Proposed initial deployment: attach to a running **desktop local/hotseat game**, use Human slots for external controllers, and expose a versioned JSON API over loopback HTTP with per-session credentials. Other transports can adapt the same contract later. No separate headless game launcher, Android server, or rewrite of the existing full-save multiplayer server is required. Existing online multiplayer behavior must remain compatible during refactoring; remotely hosting an online game through this API, including online chat and account/friend operations, can be a later extension. The host and its saves, debugger, admin credentials and other player sessions remain inaccessible to agent processes.

Recommended host defaults: one writer/controller per civilization; explicit host-controlled handoff between human and agent; sequential turns; retain the last committed observation during processing; disable undo for **both** controller types in the initial agent game; reserve load/reload/save export and spectator perspective changes for the host. A01 records the final policy. Pacing, camera controls and purely cosmetic settings remain client-local. The plan includes player resignation and postgame continuation where permitted, without granting save reload or unrestricted observation to an active player.

**How to use this backlog**

- Each checkbox is intended to be a **single reviewable PR**, with one coherent behavior change and focused tests. IDs are stable coordination labels, not dates or promised PR numbers. This is an initial decomposition; if a row grows into multiple independently reviewable changes, split it into child IDs and update dependencies before implementation.
- **Depends on** means a hard merge prerequisite, including the transitive prerequisites of those IDs. A dependent branch may be developed against its prerequisite branch and opened as a stacked draft PR. It must pass checks against the actual merged base before merging.
- **Linked work** is listed separately after the backlog. Agree on the shared signatures/decision kinds and work concurrently, but merge each PR independently in dependency order. Being linked does not introduce another hard prerequisite.
- Feature PRs include their relevant query/options, validated command, human caller migration, and permission/parity tests. If the query migration is itself substantial, land it as a separate prerequisite. Do not postpone authorization, hidden-state filtering or tests to a final security PR.
- Preserve working human flows after every merge. Keep temporary **trusted** adapters for callers that have not migrated, with explicit replacement owners. Never expose those adapters remotely. Do not remove a getter or gate a factory before supplying what its actual callers need.
- Add response fields and commands only through an explicit export allowlist. Advertise only implemented and audited capabilities. Never silently fall back from an unsupported API command to a UI closure, raw manager or full-game serializer.
- Each feature owns its export mapping/registration and contract tests once I01 exists. Earlier feature PRs include the concrete projection/handler tests; their small registration follow-ups are linked child PRs after I01. Keep this work with the feature owner rather than collecting all registrations into the final integration PR.
- Each owner updates the coverage ledger from A01 and this file when opening/merging a PR: owner, branch/PR link, actual dependencies, checks, acceptance evidence, and any split child steps. Check a box only after its acceptance criteria are met and the implementation is merged.

Use a small concrete service or result type where it suffices; the names below are conceptual boundaries, not a requirement to introduce a new module/interface for every row. Follow the repository's [coding standards](../../Unciv/docs/Developers/Coding-standards.md), particularly avoiding premature abstraction.

**Milestones and first batch**

| Milestone | Required closure | Meaning |
| --- | --- | --- |
| M0: enforceable foundation | A01, V01–V16, H01–H09 | Safe projection conventions and guarded factories/actions exist; state replacement and controller coordination have tests. This is not full action-precondition coverage or a public API release. |
| M1: safe read-only connection | I02 and its full dependency closure | An isolated external client can inspect only the implemented player observations. Additional query families remain unavailable until audited. No remote mutations. |
| M2: restricted multi-agent playtest | I06 and its full dependency closure | Two externally controlled Human slots play the documented subset through the actual running host. Unsupported mechanics/mandatory choices are explicit limitations, not bypassed. |
| M3: full bundled-game capability | I07, I08 and their full dependency closure | All bundled human actions/info surfaces are covered, concurrency and information-isolation acceptance passes, and repeatable multi-client setup is documented. |

Milestones describe dependency closure rather than a forced waterfall: M1/M2 can be developed while unrelated full-parity features are in flight. A restricted scenario must enable only rules/features for which its required actions/decisions are supported, or stop safely when unsupported decisions arise. M3 requires both bundled rulesets and their supported nation-specific abilities.

Start with **A01**, then develop **V01 and V02 in parallel**. Once V01's small context contract exists, **V04 and V06** can proceed independently; **V03** follows V01/V02, and **V05** follows V04. After V06, parallelize map geometry/resources (V07), remembered-state storage (V08), static rules (V15), and the eligible own/foreign projections. H01 starts as soon as its own dependencies merge; it does not wait for every overview or gameplay command.

Once H01/H04 and the relevant observations exist, useful independent contributor tracks are **movement/workers**, **city production/population**, **research/policies**, **diplomacy/trade**, and **historical observations**. Religion and espionage start after their read/decision contracts, while the host/transport owner continues lifecycle and connection work. Use the linked groups for interface coordination, not to turn any of these tracks into one PR.

**Validation and review rules**

Each implementation PR should prove its own behavior and permissions before merge. Use existing [TestGame](../../Unciv/tests/src/com/unciv/testing/TestGame.kt)/test-runner support. Run focused tests such as `./gradlew tests:test --tests '<relevant class>'`, then the repository's required compilation, purity, test and platform checks appropriate to the touched modules. Follow actual CI definitions rather than treating a documentation example as the complete check list. Save-schema PRs include old-save, round-trip and clone checks. UI migrations include a reproducible fixture and the specific human controls to exercise.

For changed player observations, use paired states that differ only in information the player must not know. Compare complete responses, nested fields, IDs/order/counts, preview options, refusal reasons and published tokens. For commands, test successful human/API equivalence and failure without unauthorized mutation; legitimate discovery during a real action may change the observation. For stateful grants, test later fog/invisibility, capture/death, spy departure, revocation, load and perspective changes. Schema and alias checks complement these tests; annotations alone do not prove permission enforcement.

No final audit can compensate for an unsafe intermediate exported feature. Keep security regressions with the fix. I06 and J01–J05 test composition; I07 checks coverage. They should not be the first tests for permissions, double spending, history or retries. Do not claim protection from arbitrary access to the host's filesystem/process or from unspecified CPU/network timing channels: deployment isolation and the exact observable contract are part of A01/I08.

Use this short PR record in descriptions or the coverage ledger:

```text
Plan step:
Owner / branch / PR:
Problem and resulting human/API behavior:
Hard prerequisites (merged or stacked):
Linked work / shared contract:
Exact controls or information surfaces migrated:
Command/query additions and permission rule:
Legacy adapter retired, or remaining owner:
Tests and acceptance fixture:
Save/schema compatibility, if affected:
Export state (internal, read-only, restricted, complete):
```

If a maintainer asks for a smaller change, split by a concrete query, command family, producer/consumer migration, or per-domain caller cleanup. Keep each resulting PR buildable with its own tests and prerequisites. Never split a permission fix from the test that demonstrates it, or expose a command before its live validation and safe output exist.
